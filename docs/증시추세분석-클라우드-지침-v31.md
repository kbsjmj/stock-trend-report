## v30 추가 사항: 월요일 보고서 (2026-11-02 사용자 지시)

이 절은 아래 모든 절보다 우선한다.

1. **월요일 데이터 기준**: 월요일에는 직전 금요일 마감 값을 쓴다.
   - 미국 증시: 미국 시간 금요일 정규장 마감 값.
   - 국내 증시: 한국 시간 금요일 마감 값.
2. **작성일과 제목**: 보고서는 월요일 날짜로 새로 작성한다. 제목·머리글의 작성일과 파일명(작성일 기준)은 월요일 날짜를 쓴다. 머리글 기준 문구는 금요일 날짜를 쓴다(예: "기준: 미국 10/30(금) 정규장 마감 · 한국 10/30(금) 마감").
3. **새로 작성**: 금요일 보고서를 재사용하지 않는다. 1절 원인 서술도 월요일 날짜 기준으로 4-4절 규칙에 따라 새로 쓴다.
4. **카카오톡**: 월요일 보고서를 발행하면 7절 규칙대로 카카오톡으로 보낸다. 문구의 작성일은 월요일, 기준은 금요일로 쓴다.
5. **화~금**: 기존 규칙(전 거래일 기준)을 그대로 쓴다. 토·일에는 발행하지 않는다.
6. **구현 상태**: 현재 자동 발행 코드는 기준일 하나로 발행 여부와 파일명을 정한다. 그래서 월요일 작성일과 금요일 기준일을 따로 다루지 못한다. 이 구분을 코드에 넣는 작업은 사용자 승인 후 한다. 그 전까지 자동 발행은 금요일 기록을 "이미 발행됨"으로 건너뛸 수 있다.
7. **정정**: v29 10절의 "2026-11-02 실행 기준일은 10/31"은 잘못된 내용이다. 월요일 기준일은 금요일 10/30이다.

### 4-4. 1절 원인 서술 작성 규칙 (v17 7항 통합)

1. **형식**: 1-1(미국)과 1-2(국내)는 같은 형식이다. 개요는 1~2줄로 지수 등락과 큰 흐름을 쓴다. 이어서 "상승 요인" 또는 "하락 요인"을 항목 2~3개로 쓴다. 각 항목은 3줄 이내이고 끝에 매체명을 괄호로 붙인다. 예: `(블록미디어, 글로벌이코노믹)`.
2. **"확인 불가" 금지**: 기본값이나 끝맺음으로 쓰지 않는다. 교차 검증이 부족하면 후보 원인 가운데 신뢰도가 가장 높은 내용을 고른다. 고르는 기준은 (가) 여러 매체의 공통 내용, (나) 공식 발표·지수 값·투자자별 수급과의 일치, (다) 기준일 당일의 시간 순서다.
3. **신뢰도 표시**: 두 곳 이상 일치하면 그대로 쓴다. 한 곳만 확인되면 "(단일 출처)"를 붙인다. 추정이 섞이면 "…로 보인다"로 쓰고, 추측을 사실처럼 단정하지 않는다.
4. **조사**: 서로 다른 검색어로 최소 3회 검색하고, 핵심 후보의 원문 기사를 열어 기사 날짜가 기준일과 맞는지 확인한다.
5. **수치**: `data/report_data_{기준일}.json`과 맞춘다. 매체 간 수치 차이는 주석으로 밝히고, 공식 값(KRX·지수 종가)을 쓴다.
6. **금지**: HTML 태그, 투자 권유 문구.
7. **점검 (push 전)**: "확인 불가"가 없는지, 모든 요인에 매체명이 있는지, 1-1과 1-2의 형식이 같은지 본다.
8. **적용 범위**: 이 규칙은 다음 발행부터 적용한다. 이미 발행된 보고서의 1절은 사용자 지시 없이 다시 쓰지 않는다.

## 5. 보고서 날짜와 파일 명명

- **제목·머리글**: 제목 `증시추세분석 (YYYYMMDD)`, 머리글 "작성 MM/DD · 기준: 미국 MM/DD 정규장 마감 · 한국 MM/DD 마감".
- **날짜 기준**: 파일명 YYYYMMDD는 현재 작성일을 쓴다(v18 기준). 기준일과 작성일 중 무엇을 쓸지는 미결 M5.
- **파일 이름 (보고서)**: `증시추세분석 (YYYYMMDD)-vN.pdf`. 괄호 앞에 공백, 버전은 `-vN`(하이픈), 확장자는 소문자 `.pdf`. 예: `증시추세분석 (20261031)-v18.pdf`.
- **버전 N**: 같은 날짜의 보고서 중 가장 큰 번호에 1을 더한다. 첫 발행본은 `-v1`이다.
- **공식본**: 같은 날짜에 여러 버전이 있으면 컨텍스트에 공식본을 적는다. 2026-11-01 기준 `20261031`의 공식본은 **v18**이다. v1~v17은 보관하며 삭제하지 않는다.
- **옛 이름**: `증시추세분석(YYYYMMDD)_vN.PDF`, `_vN` 표기는 쓰지 않는다. 자동 예약 프롬프트의 옛 이름은 M2에서 고친다.
- **지침·컨텍스트·실행방법 파일 이름**: `증시추세분석-클라우드-지침-vN.md`, `증시추세분석-클라우드-컨텍스트-vN.md`, `증시추세분석-클라우드-실행방법-vN.md`. 세 문서의 N은 항상 같다. 세 문서 중 하나라도 새 버전으로 저장하면 나머지 둘도 같은 번호로 함께 저장한다. 새 번호는 세 문서의 현재 번호 중 가장 큰 값에 1을 더한다. 각 문서 제목의 `(vN)`도 파일 이름의 N과 맞춘다.
- **저장 위치**: 모든 파일은 Mac 폴더 `/Users/KBS/kbsjmj/05-Project/04-증시추세분석(클라우드)`에 저장한다. 같은 이름이 있으면 덮어쓰지 않고 중단하고 알린다.

## 6. 발행과 확인 절차

1. **자동 발행**: GitHub `daily-report`가 07:00 KST(늦을 수 있음)에 실행된다. 06:28 예약 작업이 narrative를 push하여 발행을 트리거할 수도 있다.
2. **발행 확인**: `state/published/{DATE}_v*.json`에서 `drive_file_id`, `webViewLink`, 그리고 anyone(reader) 권한을 확인한다. 기록이 없으면 "발행 실패"로 보고한다.
3. **Mac 저장**: 발행된 PDF만 저장한다. 이름은 `증시추세분석 (WRITE)-vN.pdf`이다(옛 이름 금지). 저장 후 파일 크기로 확인한다.
4. **수동 수정본**: 파이프라인 밖에서 PDF를 고친 경우(예: v18의 3-1 표) 새 버전 번호로 저장하고, 수정 내역과 "PDF 직접 수정"을 컨텍스트에 기록한다. 같은 내용을 파이프라인에 반영하기 전에는 자동본과 다르다는 점을 알린다.
5. **재발행**: 강제 재발행(`force`)은 사용자가 그 날짜를 지정해 지시한 경우에만 1회 실행한다. 이미 발행된 날짜는 예약 작업이 다시 발행하지 않는다.
6. **narrative 파일**: `narrative/{DATE}.json`, 형식 `{"us": [개요, 원인…], "kr": [개요, 원인…]}`. HTML 태그를 쓰지 않는다.
